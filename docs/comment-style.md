# 注释规范

> 这不是风格偏好，而是本项目的交付标准：注释解释**为什么**，代码负责**做什么**。
> `npm run check:docs` 会校验结构；语义质量靠 review 与自觉。

---

## 1. 文件头：五个标签

每个 `src/**/*.{ts,tsx}` 文件必须以 JSDoc 开头，包含：

```ts
/**
 * @file 工具执行管线
 * @responsibility 把模型的一条工具调用，从原始 JSON 变成可回填的消息。
 * @invariants
 *   1. 无论成功失败，返回值都能转成一条 tool 消息。
 *   2. 取消只把成功降级为 ABORTED，不覆盖更具体的错误码。
 * @failureModes 未知工具 / 参数非法 / 审批拒绝 / 超时 / 取消 / 执行异常
 * @concepts docs/concepts/tool-contract.md
 */
```

- `@responsibility`：一句话说清边界。写不出来，说明模块该拆了。
- `@invariants`：调用方可以依赖、实现方不能违反的性质。这是最值钱的一栏。
- `@failureModes`：出错时会发生什么、如何表达。没有它，读者会以为世界永远正常。
- `@concepts`：指向概念文档；`check:docs` 会验证路径存在。

## 2. 导出符号：必须有 JSDoc

每个 `export`（函数、类、接口、类型、常量）上方要有 JSDoc。函数至少说明：

- 它为什么存在（不是"返回一个 X"，而是"为什么需要这个 X"）；
- 参数/返回值的语义；
- 会抛出什么错误（用 `@throws` 或正文说明）；
- 有副作用时写明副作用。

**反例**（只复述类型）：

```ts
/** 返回 config。 */
export function parseConfig(input: unknown): Config { ... }
```

**正例**（解释约束与失败）：

```ts
/**
 * 校验并补全配置。
 *
 * 为什么把 zod 的 issue 重新拼成字符串？
 * 学习者需要看到"哪个字段错了"；details 里保留原始 issue 供程序化消费。
 *
 * @throws AgentError INVALID_CONFIG —— 输入不符合 schema 时。
 */
```

## 3. 关键算法：分段 + 说清取舍

- SSE 分包、压缩区域选择、路径规范化、进程树终止：每一步前写一句"为什么这样"。
- 有平台差异（Windows `taskkill /T`、CRLF、大小写）必须就地说明原因。
- 复杂结构用 ASCII 小图，比三段散文有效。

**取舍注释**是本仓库最重要的注释类型：

```ts
// 为什么先校验再审批？
// 审批弹窗要展示"将要执行的参数"，所以必须是校验并规范化后的输入；
// 否则用户批准的和实际执行的可能不是同一份数据（TOCTOU）。
```

## 4. 明确不要写的

| 不要 | 原因 |
|---|---|
| `// 自增 i` | 复述代码，零信息量 |
| `// TODO` 却不写条件 | 无法判断何时该做 |
| 过时的注释 | 比没有注释更危险；改代码必须同步改注释 |
| 大段复制外部文档 | 链接到 `docs/concepts/`，保持单一来源 |
| 用注释解释"显然"的语法 | 浪费读者注意力 |

## 5. 测试也是文档

- `describe` 标题写"证明什么"，例如「证明默认值自洽」；
- 关键用例上方注明它对应哪条红线（P1–P11 / S1–S8）；
- 断言失败时，读者应该能从测试名知道哪条契约被破坏了。

## 6. `check:docs` 的边界

脚本做四件事（启发式）：

1. 文件头存在且含五个标签；
2. `@concepts` 路径存在；
3. 每个 export 上方有 JSDoc 块；
4. 已勾选步骤有对应笔记。

它**不检查**语义质量、不解析 AST、不检查注释是否过时。漏网的部分靠 code review；
但结构性的偷懒（不写文件头、不给导出写说明）会被 CI 直接拦下。

## 7. 语言

- 注释、文档、学习笔记：**中文**（术语首次出现附英文）。
- 标识符、类型名、commit message：**英文**。
- 错误消息：中文（面向使用者），但错误码是稳定的英文枚举。
