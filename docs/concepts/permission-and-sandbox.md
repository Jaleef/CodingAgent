# 权限与沙箱

## 一句话

默认拒绝；每次敏感操作要么有明确策略放行，要么由人当场批准，并留下可审计的记录。

## 三档模式

| 模式 | 文件 | shell | 适用场景 |
|---|---|---|---|
| `read-only` | 只读 | 只读白名单 | 调研、review、答疑 |
| `workspace-write` | 工作区内可写 | 变更类命令默认询问 | 日常开发（默认） |
| `danger-full-access` | 全盘 | 全命令（灾难命令仍拦） | 明确的自动化/容器环境 |

模式是"上限"，不是"一律放行"：即使 `danger-full-access`，`rm -rf /` 这类命令仍然 deny。

## 决策与执行是两层

1. **决策层**：这个操作属于 allow / deny / ask？
2. **执行层**：路径是否在工作区内？命令是否在黑名单里？

决策层不关心具体路径，执行层不关心用户意图；两层分开才好测试。

## 默认拒绝（fail-closed）

- 无审批通道（非 TTY、CI、`--print`）→ ask 一律视为 deny；
- 审批超时 → deny；
- 权限引擎异常 → deny。

这比"出错就放行"安全得多，代价是自动化场景需要显式 `--yes`。

## 审批不是橡皮图章

审批弹窗必须展示**校验并规范化之后**的参数：

- 命令全文，而不是截断后的摘要；
- 文件 diff，而不是"将写入某文件"；
- 风险等级与默认答案（默认 deny）。

否则用户批准的和实际执行的可能不是同一份数据（TOCTOU）。

## 策略沙箱 ≠ 操作系统沙箱

本仓库 v1 只做：

- 路径规范化与工作区边界检查；
- 命令风险分类；
- 人工审批。

它防不住恶意进程、提权、容器逃逸。真正的隔离需要 OS 能力（AppContainer/ACL、bubblewrap），
不在 v1 范围内。把策略沙箱当安全边界，是最危险的误用。

## 带着这些问题读

1. 为什么 `ask` 不是最终态？
2. 非交互模式下，为什么默认 deny 而不是默认 allow？
3. 路径检查为什么要先解析符号链接？
4. 审批的"本会话允许"应该记住什么粒度（工具？命令前缀？路径）？

## 常见误解

- **"只读模式绝对安全"**：只读工具也可能把敏感内容带进上下文（密钥、隐私）。
- **"danger-full-access 等于关掉检查"**：灾难命令仍然拦，审计仍然记录。
- **"审批弹窗只是 UI"**：它是安全链路的一环，展示内容必须与执行内容一致。
