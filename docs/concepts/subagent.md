# 子代理（subagent）

## 一句话

把独立子任务交给一个**拥有全新上下文**的代理去跑，只把摘要带回父会话。

## 为什么需要隔离

父会话的上下文很贵：每个 token 都影响成本、延迟与缓存。如果让子任务的全部工具输出
都进父上下文，几个搜索就能把窗口塞满。

子代理的做法是：

```
父会话（上下文 A）
  └─ 派生子代理（上下文 B：只含任务描述）
        └─ 读文件、跑命令、反复试错……
  ← 只返回 summary（+ 用量 + 子会话 id）
```

父上下文只增加一条 tool 结果，而不是几百条中间消息。

## 关键约束

1. **独立会话**：子代理有自己的 session 文件，通过 `parentSessionId` 关联；
2. **只回摘要**：子转录不进入父上下文；
3. **只减不增**：子代理权限是父权限的子集；
4. **深度为 1**：v1 不允许子代理再派生子代理（防递归爆炸）；
5. **可取消**：父级取消必须级联到子级；
6. **有预算**：并发数、超时、最大步数都要有上限。

## 结果与成本

返回给父会话的是 `SubagentResult`：

```
{ status, summary, sessionId, usage? }
```

`sessionId` 让审计可以追到子会话；`usage` 用于把子代理的 token 成本汇总到父级。

## 带着这些问题读

1. 为什么子代理看不到父对话？这对任务描述提出了什么要求？
2. 子代理需要审批时，谁来做决定？
3. 父代理取消后，子代理的进程/请求如何收尾？
4. 子代理的 token 成本应该记在谁头上？

## 常见误解

- **"子代理是为了并行加速"**：主要目的是上下文隔离；并行只是附带收益。
- **"把父对话复制给子代理更省事"**：那就失去了隔离的意义，还会放大成本。
- **"子代理可以随便开"**：并发与深度必须有硬上限，否则会指数级消耗。
