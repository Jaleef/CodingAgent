# 工具契约

## 一句话

工具 = 名字 + 描述 + 参数 schema + 执行体；**模型只能看到前三者中的前三个字段**，
执行体、超时、渲染回调永远不下发。

## 为什么需要"投影"

内核里的工具定义包含很多信息：zod schema、执行函数、超时、结果上限、UI 渲染。
但模型只需要知道"叫什么、能做什么、参数长什么样"。

把完整定义直接序列化给模型会带来三个问题：

1. **浪费 token**：执行代码对模型毫无意义；
2. **泄漏内部**：函数名、实现细节可能被模型利用或误读；
3. **破坏缓存**：任何内部字段变化都会改变请求前缀。

所以注册表在请求时做一次**投影**：`{ name, description, input_schema }`。
这是红线 P1 的直接落点。

## 单一 schema 真源

参数 schema 用 zod 定义一次，然后：

- 用 `z.toJSONSchema()` 生成模型可见的 JSON Schema；
- 用同一个 zod schema 校验模型返回的参数。

两处各写一份 schema 是 bug 的温床：模型按 A 调用，校验按 B 拒绝。

## 失败是数据，不是异常

工具失败（文件不存在、命令超时、审批被拒）应该返回一个 `ToolOutcome`：

```
{ content: [...], isError: true, errorCode: "TOOL_TIMEOUT" }
```

这样模型能看到错误并调整策略。只有"管线本身坏了"（实现 bug）才允许 throw。

## 读后写

`write` / `edit` 之前必须有一次匹配的 `read` 观测（mtime + size）。
原因：模型可能在读完之后，用户或其他进程改了文件；直接写会静默覆盖别人的修改。

这不是文件工具独有的洁癖，而是 harness 的通用约束：**副作用必须基于已观察到的状态**。

## 带着这些问题读

1. 为什么工具参数要用 zod，而不是手写 JSON Schema？
2. 审批弹窗展示的参数，和最终执行的参数，如何保证是同一份？
3. 工具超时和用户取消，错误码应该如何区分？
4. 工具越多越好吗？工具数量对选择准确率有什么影响？

## 常见误解

- **"工具就是函数"**：模型看到的工具是"描述"，函数只是实现；描述写不好，工具等于不存在。
- **"报错就 throw"**：throw 会中断整个 turn，而模型本可以自我修正。
- **"并发安全就是无状态"**：还要考虑同一文件的写冲突与结果顺序。
